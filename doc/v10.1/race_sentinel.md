## 1. Why a home-made detector

From `methods_backlog.md` §0.2 (measured, not assumed):

- ThreadSanitizer has no Windows support and MSYS2 gcc 16.1.0 ships no
  `libtsan`; there is also no `libasan` — so the usual answer “just turn on the
  sanitizer” does not exist here.
- clang/gdb/cdb are not installed; `-D_GLIBCXX_DEBUG` sidecar fails to link
  (conan ABI conflict). PageHeap only gives the *write* stack after corruption,
  not the concurrent accessor.

M1 therefore proposes an Eraser-style **lockset** detector with LiteRace-style
**sampling**, built as test-only code: instrument the containers the project
already suspects, run the four already-fixed race *patterns* as controls, and
decide by numbers (detection rate, false positives, overhead) whether it is
worth wiring into the product path (Phase 2).

## 3. Detector design

### 3.1 Data structures and algorithm (Eraser, 1997 + sampling)

`RaceTrack<Container>` forwards to the wrapped `std::vector / std::string /
std::map / std::unordered_map` and, for every operation, calls
`race_sentinel::touch(elementId, isWrite, opName)`:

- every container also has one **structural slot** (`meta`): `push_back`,
  `operator[]` insert, `erase`, `begin/end`, `resize`-like operations touch it;
- **element slots** are keyed by a hash of the identity: vector index, map key,
  or a single slot for the whole `std::string`;
- per slot the detector stores the last writer and the last reader as
  `(thread id, happens-before epoch, lockset, thread label, operation name)`;
- an access is a **race candidate** iff, against the last opposing access
  (read vs write; for a write also write vs write):
  - threads differ, **and**
  - no happens-before edge exists (`prev.epoch >= my.epoch`), **and**
  - the lockset intersection is empty (`(prev.locks & my.locks).none()`).

Read/read pairs are never reported. Same-thread pairs are never reported.
A slot reports at most once per `resetAll()` (bounded report memory, useful
ranking in Phase 2). Up to 4096 reports are stored; the counter keeps counting.

### 3.2 Locks the detector can see

Only `race_sentinel::TrackedMutex` (an `std::mutex` with an id and a per-thread
re-entrant depth counter). This is the central Phase-1 restriction: the detector
must not modify product mutexes, so the negative controls use `TrackedMutex`
explicitly. Phase 2 replaces this with hooks on the product lock wrappers
(§8).

The lockset is a 64-bit mask, so at most 63 `TrackedMutex` instances can be
tracked at the same time. Ids are recycled when a `TrackedMutex` is destroyed,
because an experiment creates one mutex per control run (hundreds of them in a
soak); with more than 63 *live* tracked mutexes the surplus degrades to
"untracked" and the detector must be treated as blind for those objects.

### 3.3 Happens-before model (coarse epoch)

A single global `epoch` is advanced by:

- `beginConcurrent()` — once per group of threads that will race; all members
  inherit the same epoch (so accesses between them are *concurrent*);
- `joinTracked(t)` — join, then advance the caller’s epoch, so everything the
  joined thread did happens-before the caller’s later accesses.

A recorded access whose epoch is strictly lower than the accessing thread’s
current epoch is treated as happens-before. This is sound for
thread-spawn/thread-join edges (which is all the controls need) and is
deliberately conservative: the blind spots can only produce **false negatives**,
not false positives on lock-correct code. Phase 2 replaces it with per-thread
vector clocks (§8.5).

### 3.4 Sampling (1/N)

`touch()` first increments a thread-local counter and instruments only every
N-th operation (`RACE_SENTINEL_SAMPLE`, default **16**; 1/100 as originally
written in M1 would be too sparse for short Phase-1 windows and no better for
overhead here). Slot state persists between sampled accesses, so in a hot race
the first *sampled* cross-thread conflicting pair is found — measured median
first report is 0.3–0.9 ms (§4.3).

### 3.5 Activation

`RACE_SENTINEL=1` at process start arms the detector; otherwise every
`RaceTrack` method is a plain forward and `TrackedMutex` is an `std::mutex`
(one predictable atomic-load branch per operation). This gives the
“no instrumentation” reference run for free in the same binary —
`race_sentinel::setActiveForTesting(false/true)` is the test hook.

### 3.6 Reports

`Report` carries element slot id, both thread ids, both epochs, both locksets,
both thread labels and both operation names, plus `since_reset_ms`. Threads set
a label with `setThreadLabel()`; the workloads use `A/B` and operation names
such as `push_back.structure`, `iter-deref`, `find`, `assign`.
Example from the run: `A/push_back.structure -> B/begin` (pattern A),
`A/assign -> B/assign` (pattern B), `B/find -> A/operator[]` (patterns C/D).

No stack capture in Phase 1 (no symbolizer on MinGW); Phase 2 adds a caller-site
id and resolves it against the linker map (§8.5).

## 4. Control experiment

### 4.1 Positive controls — standalone reproductions of the four fixed patterns

No product source is used or modified; each pattern is written from scratch and
**shaped so the harness itself cannot corrupt the heap** (otherwise the
experiment would measure the crash, not the detector):

| ID | Pattern (from `crash_forensics_2026-11-15.md`) | Harness-safety shaping |
|---|---|---|
| A | lazy `vector::push_back` while another thread iterates | capacity `reserve(8192)` up-front; writer never grows past 4000 → race is on size()/elements, memory stays allocated |
| B | process-global `std::string` written from two threads | only SSO assignments (7–8 chars) → no shared heap buffer |
| C | bare `std::map::operator[]` insert racing a reader | insertion bounded to 256 keys, then value-only writes; nodes are never freed |
| D | `unordered_map::erase` racing `find` | custom never-freeing arena allocator keeps erased nodes mapped → the structural race stays, the use-after-free AV disappears |

Each run: fresh container, main thread initialises, `resetAll()`, two worker
threads start on a barrier with the **same** epoch, main polls
`reportCount()` for up to `PositiveWindowMs` (500 ms) and stops the workers on
the first report. Seed (0…19) drives thread jitter (`yield`) and key choices.

### 4.2 Negative controls

The same four patterns with every container access under one
`TrackedMutex` (per-operation locking so the threads still interleave).
Observation window 2500 ms per run; **must produce zero reports**.  A negative
run always consumes the full window even if a report appears (otherwise one
false positive would truncate the very exposure used to measure the FP rate).
Each run creates a fresh `TrackedMutex`; the detector recycles lockset ids on
destruction (found the hard way: the first `-SoakMinutes` validation run created
more than 63 mutex instances, exhausted the 64-bit lockset, and produced 4310
false positives — see §5). Runs are
split across 4 parallel processes (each process = a disjoint seed range) to
build aggregate exposure cheaply: 80 runs × 2.5 s = **200 s** of instrumented
negative-control workload in 50 s wall time.

### 4.3 Metric definitions

- **Detection rate** = runs with ≥ 1 report / total runs, per pattern and
  aggregate; **first-report latency** = time from run start to the first report.
- **False positives per 30 min** = reports on the negative controls, reported as
  (a) the *observed point estimate*: `reports × 1800 / exposure_seconds`, and
  (b) the 95 % upper bound via rule of three: `3 × 1800 / exposure_seconds`.
- **Overhead multiplier** = median over reps of `instrumented mean / suspended
  mean` on fixed-op-count locked workloads, per pattern (2 threads ×
  `RACE_SENTINEL_OPS` operations each), then aggregated as a geometric mean.
  “Uninstrumented” is the *same code path with the detector suspended* (not raw
  containers), so the multiplier isolates instrumentation cost.

## 5. Harness correctness tests (also in the full gtest suite)

`RaceSentinelControls.*` — 4 positives must be detected, 4 negatives must be
silent (each 800 ms window, `sampled > 0` asserted to prove instrumentation ran).

`RaceSentinelUnit.*` — activation hook, sampling rate, inactive pass-through is
silent, spawn edge suppresses pre-spawn writes, join edge suppresses post-join
reads, different lock-sets are reported, same-thread is never flagged,
per-element dedupe, decorator preserves container semantics, lockset tracking
through `TrackedMutex`, lock-id recycling across hundreds of mutex instances,
and a "100 short negative runs stay silent" soak-shape regression.

The soak-shape tests earned their place: the first `-SoakMinutes 1` validation
run (long seed range, one mutex per run) created > 63 mutexes, exhausted the
64-bit lockset, and produced **4310 false positives** in 64 s — a detector
defect, not a product race. Fix: recycle lock ids on `TrackedMutex` destruction
(`LockIdsAreRecycledAcrossManyMutexInstances`,
`ManyShortNegativeRunsStaySilent`); re-validation gave 0 reports over 121 s of
soak-shaped exposure. This is exactly the kind of self-check the Phase-1
experiment exists for.

`RaceSentinelExperiment.Matrix` — the driver entry point; `GTEST_SKIP()` unless
`RACE_SENTINEL_MODE` is set, so a normal regression run is unaffected.

## 6. What a report means (and does not mean)

A report is a **race candidate**, not a proof: the detector has no access to
product locks in Phase 1, so it proves only “two accesses to the same slot, at
least one a write, by different threads, with no common detector-visible lock
and no spawn/join ordering”. That is exactly what Eraser reports; the Phase-2
reviewer has to check the two operation names + labels against the source.

Conversely, silence is not a proof of correctness: see the blind spots in §7.1.

## 7. Limits (honest)

### 7.1 Blind spots (produce false negatives)

1. **Locks it cannot see**: raw `std::mutex`, `std::shared_mutex`, condition
   variables, atomics used as hand-offs/flag publication, `std::async` futures,
   `std::once_flag`, TLS tricks. Anything synchronised only that way looks
   unsynchronised.
2. **Coarse epoch**: only spawn-group/join edges. Two threads spawned in
   different groups without a join look concurrent; a hand-off through an atomic
   looks racy. Different groups also lose HB between them (false negatives).
3. **Sampling 1/16**: a race window hit fewer than ~tens of times per second may
   never be sampled. The Phase-1 controls are maximum-density patterns; real
   windows are much sparser — that is why Phase 2 needs a 30 min soak, not a
   0.5 s run.
4. **Element identity by hash**: vector index / map-key hash / a single slot for
   the whole string. Two distinct objects can share a slot only on a 64-bit hash
   collision (negligible), but reallocation of a container changes addresses in a
   way the decorator does not model (it models identity, not address). A pure
   address-based detector (TSan) would report moves/reallocations differently.
5. **Container coverage**: only the four decorated types; `std::deque`,
   `std::set`, arrays of structs, custom maps are not covered.
6. **Only 63 simultaneously live tracked locks**: the lockset is a 64-bit mask
   and ids are recycled per `TrackedMutex` instance, so a workload that keeps
   more than 63 tracked mutexes alive at once leaves the surplus untracked.
7. **No stacks**: reports carry labels/operation names, not call sites (Phase 2
   adds site id + map symbolisation).

### 7.2 False-positive accounting

Observed false positives: **0 over 200 s / 58.2 M sampled accesses**. The
“per 30 min” point estimate is therefore 0, which passes the M1 threshold.
However, certifying “≤ 1 per 30 min” at 95 % confidence with zero events needs
**≥ 90 min of aggregate exposure** (rule of three: `3 × 1800 / 5400 s = 1`).
The driver supports this directly:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\race_sentinel_run.ps1 -SoakMinutes 90
```

(~23 min wall at 4 parallel streams, ~90 min aggregate exposure; still does not
touch the live gateway). Until that is run, treat the FP number as *observed 0*
rather than *statistically certified ≤ 1*; the report prints both.

### 7.3 Classification conservatism

Non-const `operator[]` is classified as a **write** (a vector reader using
`v[i]` on a non-const object is treated as a writer). In the negative controls
this is harmless (common lock), but on product code it can produce false
positives where read-only access goes through a non-const `operator[]` under a
different lock. Phase 2 should add a `read_only` accessor or classify by
constness at the call site.

### 8.1 Concrete first targets (from `round_2026-11-15.md` §7, verified in-tree)

1. **`mcpActionMap_` (unlocked read vs locked write)** — the strongest match for
   the pattern the detector proves it can catch.
   - declaration: `autonomy_stack.hpp:494`
     `std::map<std::string, std::pair<std::string, std::string>> mcpActionMap_;`
   - **unlocked read**: `autonomy_stack.cpp:1135`
     `auto it = mcpActionMap_.find(spec.name);` inside `executeAgiAction`’s

### 8.2 Instrumentation mechanism (minimum diff, reversible)

- Add `#include "tests/gtest/support/race_track.hpp"` to the target TUs and
  change the four member declarations + the enclosing `std::mutex` members to
  `race_sentinel::RaceTrack<…>` / `race_sentinel::TrackedMutex`, all inside
  `#ifdef PHOENIX_RACE_SENTINEL` so the shipped build is byte-identical when the
  macro is off.
- Build with the existing sidecar pattern `build\tmp\compile_next.bat`
  (`phoenix_main.next.exe`), **never** `compile.bat` (it taskkills the live
  gateway and the llama-servers). A sidecar must also get its own port
  (5101) and working directory (`build\tmp\race_sentinel\soak\`) per
  `crash_hunt_pageheap.md` §3.
- The same binary is its own control: `RACE_SENTINEL` unset → detector is a
  pass-through, so “armed vs unarmed” overhead and behaviour are directly
  comparable (Phase 1 measured the multiplier on exactly that principle).
- Dump reports: env-gated exit hook or a debug route
  (`/api/debug/race_reports`) that serialises `race_sentinel::reports()` to
  `build\tmp\race_sentinel\soak\reports.json`; a static destructor is not
  reliable because the process is killed on E-stop.

### 8.3 Workload for the 30 min soak

Per `methods_backlog.md` M1: sidecar port 5101 + isolated workdir + **8 parallel
missions** (the `mission.layer`/`replicate` API from `mission_layer.md`) + one
chat loop, 30 min. The three suspects need their paths exercised:
MCP tool dispatch (register a local MCP server), mission-scope GNN summary
writes (chat summary + mission tick concurrently), and outline-cache reads
during `assign`/`report`.

### 8.4 Acceptance / decision rule

1. Phase-1 controls still pass with the product build flags (regression).
2. 30 min armed soak: observed FP ≤ 1 (point estimate), and the 90 min
   rule-of-three certification from §7.2 before any gate use.
3. At least one suspect gets a report that a human reviewer can confirm as a
   real race window from the two operation names/labels; otherwise the detector
   stays a *ranking tool*, not a gate (that is the M1 “failure still valuable”
   branch).
4. Reports are ranked by element slot × count and symbolised via
   `phoenix_main.map` (`compile_next.bat` already passes `-Wl,-Map`).

### 8.5 Detector upgrades worth doing before the soak

Priority order (each is small and test-only until §8.2):

1. **Site ids + symbolisation**: record `__builtin_return_address(0)` (or a
   caller-passed site id) in `touch()` and resolve against the linker map;
   report includes the source location without a debugger.
2. **Container tag**: `RaceTrack<Container, Tag>` so reports name the member
   (`mcpActionMap_`, `ScopedTrainableMemory::live_`, …) instead of a slot hash.
3. **Vector clocks** (FastTrack) replacing the coarse epoch: removes the
   false negatives from hand-offs and from different spawn groups, which
   matters on a 30 min multi-thread product soak. This is the M1 “phase 2
   upgrade line” already noted in the method doc.
4. **Lock hooks**: a `-include` shim (or the L2 patch) that maps the product’s
   `std::mutex`/`std::shared_mutex` members to `TrackedMutex`/tracked
   `shared_mutex` instead of only test-controlled locks.
5. **Adaptive sampling** (LiteRace): sample the first access per site, then per
   site/N, to keep detection while lowering overhead on hot containers.

Estimated effort: §8.1 targets + shim ≈ 1–1.5 days; soak + review 0.5 day;
vector clocks ≈ 1 day.

### 11.4 Findings

1. **The mcp map fix is correct (static review).** In the new
   `executeAgiAction` mcp branch the `find()` runs inside
   `std::lock_guard(mu_)`, only the `mcpServer`/`mcpTool` copies escape the
   block, and `mcpManager_.callTool()` runs outside it (deliberate: holding
   `mu_` across a network tool would serialise every mission tick). No `it`
   escapes; no dereference after unlock.
2. **Debug-probe crash on the MCP configure+dispatch path (not a detector
   finding, not caused by the detector).** A probe that called
   `configureMcp()` and then dispatched an mcp.* action kills the sidecar with
   an unhandled C++ exception (`0x20474343`) followed by `0xC0000005`, even
   with one probe thread and with the detector *disarmed*. Same rip in 4
   independent runs (fatal logs under
   `build/tmp/race_sentinel/{soak_smoke2,isolate_all,mcp_verify_sequential}/`).
   After separating the harness trigger (the debug probe called product code
   from an unguarded `std::thread`; production callers of `executeAgiAction`
   do wrap it in try/catch), two product observations remain:
   - `phoenix::mcp::McpManager::startAll()` appends new `McpClient`s to
     `clients_` without clearing/stopping existing ones, so a runtime
     `configureMcp()` (config hot-update) spawns a duplicate MCP server and
     leaks the old client — a structural bug visible in `mcp_client.cpp`;
   - the MCP dispatch path can throw; `CognitionAutonomyManager::executeAgiAction`
     does not itself catch, so the try/catch discipline at call sites is
     load-bearing.
3. **No new races on the residual bucket-field writes** in this workload: chat
   and mission ticks write different scopes (`chat:<session>` vs
   `mission:<id>`), so the same-slot window did not open. Memory-probe traffic
   used one shared scope and stayed silent (the probe goes through
   `setGnnSummary`, which is fieldMu-guarded; the unguarded `hot().field =`
   sites all live on chat/mission paths with disjoint scopes).

### 11.5 Coverage gaps / next round

- The fixed mcp **read path was not dispatched** during the soak: the 8B
  deliberator does not emit tool-JSON without schema advertising, so
  `mcpActionMap_.find` was likely never hit. A dispatch-only debug probe
  (resolve the action name, call `executeAgiActionByName` in a try/catch, do
  **not** call `configureMcp`) is the missing piece; recommend adding it next
  round.
- `OnlineResearcher::cache_` was exercised via 152 research-probe loops with 0
  reports (regression negative holds). crash-fix's `fallback()` `stateMu_` guard
  was compiled in but is *outside* the detector's coverage (RuntimeState
  internals are not instrumented); it can only be validated by crash evidence,
  not by race reports.
- Fields written through `hot()` in the remaining sites and the `archived_` map
  are not instrumented; vector clocks / site symbolisation stay on the §8.5
  list.
