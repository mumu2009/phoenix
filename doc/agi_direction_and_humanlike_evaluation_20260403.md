# Phoenix 下一步方向与类人评测标准

形式化评测规范见 [algorithm/HAI_Formal_Spec.md](./algorithm/HAI_Formal_Spec.md)。

## 与当前实现对齐的校正

在继续定义 AGI 路线之前，需要先把本文和当前代码实现对齐。

1. Phoenix 当前后端是组件化、可切换的，不是强绑定外部环境。
   代码中 `transformerMode` 明确支持 `native`、`ollama`、`ollama-fine-tuning`、`llamacpp`、`bitnet`、`off`，并且 `gnnModuleDisabled`、`inferenceEnabled` 也是独立开关。这说明外部环境在架构上是可选项，而不是强制依赖。

2. 当前主在线链路里，GNN 更接近“指导过程”而不是最终答案生成器。
   代码与文档 [v3_contract.md](./v3_contract.md)、[algorithm/StreamOfData.md](./algorithm/StreamOfData.md) 一致：GNN 会输出 `graphContext` 和 `graphEmbeddings`，然后交给 `transformer_.chat(...)` 或外部 Transformer 家族后端继续生成最终 `reply`。

3. GNN 与 Transformer 当前同时存在两类共享。
   一类是 `prompt` 级共享，即 `graphContext` 进入文本上下文；另一类是张量级共享，即 `graphEmbeddings` 进入 `transformer_.chat(text, modelGraphContext, graphEmb, maxTokens)`。所以更准确的说法不是“图谱替代 Transformer”，而是“图谱在指导 Transformer”。

4. 当前连续性机制主要由前端会话层承担。
   `frontend_server.cpp` 中的 `concat/direct`、`rnn`、`lstm` 确实分别覆盖瞬时、短期、长期会话记忆。因而本文后续提到的“连续性”应主要理解为在线会话连续性与计划性交接，而不是把“完全容灾恢复”当成硬性目标。

## 目标重述

你的目标不是做一个“问答分更高的系统”，而是做一个：

- 能跨任务迁移
- 能持续记忆
- 能长期执行
- 能在环境中学习
- 能与人稳定协作

的通用智能体。

这和“把同一个模型的 QA 分再抬高一点”不是一回事。

当前报告 [intelligence_gap_analysis_20260403.md](./intelligence_gap_analysis_20260403.md) 已经说明一个关键事实：Phoenix 现在更像“强系统包装 + 外部模型适配 + 本地图推理模块”的混合体，而不是一个已经稳定成型的通用智能核心。

所以你下一步不应该继续把所有能力都塞进单次问答链路里，而应该把系统拆成更清晰的层次。

## 总方向

下一阶段建议从“追求单轮回答像人”切换到“建设一个可持续、可学习、可验证的通用智能体框架”。

核心判断只有一句话：

**Phoenix 未来应该把自己定位成智能体操作系统，而不是 prompt 前后拼接器。**

这意味着：

1. 底层大模型负责原生语言智能。
2. Phoenix 负责记忆、工具、长期目标、环境状态和学习回路。
3. 图谱、上下文、工具契约只能在“需要时”进入模型，而不是默认污染每一轮回答。

## 下一步路线

## 第一方向：先保护原生智能，再谈系统增强

当前报告里最大的警告信号不是“Phoenix 比 Ollama 低了 0.8 分”，而是 Phoenix 现在会主动改变模型输入分布。

所以第一优先级不是加更多功能，而是先建立一条 **不损伤原生模型能力的主通道**。

### 你应该立即做的事

1. 建立 `raw chat mode`
   目标：让 Phoenix 能以最小包装直通外部模型。
   要求：保留原始多角色消息，不把 `graphContext` 强塞进单条 `user` 消息。

2. 建立 `augmentation off / on` 可切换架构
   目标：任意一次评测都能明确知道当前是否启用了：
   - graph selector
   - context hint
   - addon tools
   - long query safe mode
   - verify
   - cache

3. 所有增强模块都要改成“条件触发”而不是“默认拼接”
   原则：只有在路由器判断收益大于干扰时，图谱和工具上下文才进入模型。

### 为什么这一步最重要

如果你连“系统本身是否在削弱基础模型能力”都控制不住，那后面做记忆、规划、长期学习时，所有评测都会被包装层噪声污染。

这一步的目标不是 AGI 本身，而是 **拿回一个干净基线**。

## 第二方向：把图谱从“回答生成器”降级为“知识与记忆底座”

你当前本地图推理的强项不是语言生成，而是：

- 结构化记忆
- 关联传播
- 会话历史召回
- 词到概念的映射

这其实是优点，但前提是别让它假装自己是完整的通用推理器。

### 建议的重定位

不要让图谱绕过主在线链路去充当默认的最终自然语言回答器。

更准确地说，当前主在线路径里，最终生成已经主要由 Transformer 或外部 Transformer 家族后端负责；下一步要做的不是推翻这条架构，而是继续约束 GNN 只在“指导、检索、压缩、增强”层起作用。

应该改成三种职责：

1. 语义记忆层
   存人物、概念、关系、经验片段、项目状态。

2. 检索候选层
   在回答前给出候选事实、候选经验、候选工具，而不是直接输出自然语言。

3. 长期状态层
   保存多轮任务中的中间状态、未完成子目标、失败原因、已学策略。

### 原则

图谱负责“知道什么可能相关”，大模型负责“决定怎么说、怎么推理、怎么行动”。

如果你继续让图谱模块输出最终自然语言，它会长期卡在“很像系统、不像人”的阶段。

## 第三方向：真正建设长期智能，而不是单轮智能

类人智能最重要的特征之一不是答题，而是 **长期连续性**。

在 Phoenix 当前实现里，这个问题要分成两部分：

1. 在线会话内的连续推进
2. 会话之间的计划性交接与显式保存

而不是把“任意中断后的完全容灾恢复”当成强约束。

一个更接近人的系统，应该具备：

- 同一个项目能持续几小时到几天
- 在线会话内能持续推进
- 在明确保存或交接后能继续推进
- 知道自己之前做过什么
- 能修正自己之前的错误策略
- 会形成偏好、习惯和稳定工作流

### 所以你下一阶段应该做的不是更强 QA，而是这四个子系统

1. `Episodic Memory`
   记录具体经历：谁说了什么、系统做了什么、结果如何。

2. `Semantic Memory`
   抽象出长期稳定知识：概念、规则、人物、项目背景。

3. `Procedural Memory`
   保存成功工作流：遇到某类任务时该怎么拆分、使用哪些工具、哪些顺序有效。

4. `Goal / Plan Memory`
   维护长期目标树，而不只是当前对话缓存。

### 这一步的关键指标

不是“它会不会回答”，而是“它能不能在连续会话中持续做事，并在显式交接后继续推进，而且更好”。

## 第四方向：加入环境中的闭环学习

真正接近 AGI 的系统，必须进入环境，而不是只停留在文本里。

对你现在这个项目来说，环境不一定是机器人本体，也可以是：

- 代码仓库
- 文件系统
- 浏览器
- API
- 本地工具
- 用户长期任务

### 下一步应该建设的不是更多 benchmark，而是更多闭环

建议至少建立三种闭环：

1. `Observe -> Act -> Verify -> Update Memory`
2. `Plan -> Execute -> Detect Failure -> Replan`
3. `Try -> Receive Outcome -> Learn Policy`

### 这一步的意义

没有环境闭环，系统只能“像人地说话”。

有了环境闭环，它才开始“像人一样在世界中工作”。

## 第五方向：做人类协作智能，而不是纯解题智能

类人性不能只看 QA，还有一个关键维度：**协作性**。

一个更像人的系统，应该能：

- 理解模糊需求
- 识别对方真正目标
- 在不确定时主动澄清
- 在任务过程中汇报状态
- 根据反馈调整风格
- 长期保持角色一致性和合作关系

这意味着你要把“人机协作能力”单独当成一级目标，而不是把它混在问答分里。

## 第六方向：把学习从“参数训练”扩展到“策略进化”

如果你的目标是通用、类人、长期进化，那学习不能只理解为：

- 微调模型
- 加训练数据
- 继续堆问答样本

还应该包括：

- 学会什么时候检索
- 学会什么时候用工具
- 学会什么时候保持沉默
- 学会如何规划
- 学会如何在失败后更新下一次策略

也就是说，你后续更重要的学习对象往往不是“语言模型权重”，而是：

- 路由策略
- 记忆读写策略
- 计划策略
- 自我修正策略

## 不建议的方向

基于当前报告，下面几件事不建议继续作为主线：

1. 不建议把 QA 分数当成 AGI 主目标。
2. 不建议继续默认把图谱摘要粗暴拼进 prompt。
3. 不建议把本地图推理模块继续包装成“完整通用推理器”。
4. 不建议只用单轮问答来判断类人性。
5. 不建议把“会调用工具”误判成“拥有人类智能”。

## 检测标准设计原则

你说得对，类人性不能单纯通过 QA 展现出来。

所以这里建议你把评测目标从“答得对不对”升级为“是否具备类人的通用行为结构”。

### 评测设计原则

1. 评测必须跨时间，而不是只看单轮。
2. 评测必须跨任务类型，而不是只看问答。
3. 评测必须进入环境，而不是只看文本。
4. 评测必须包含协作，而不是只看独立输出。
5. 评测必须区分“原生能力”和“外挂能力”。
6. 评测必须包含在线连续性与计划性交接能力，但不把完全容灾恢复设为硬性前提。

## 推荐的类人智能评测框架

建议建立一个 `HAI`，即 `Human-like Agency Index`。

定义：

$$
HAI = \sum_{i=1}^{8} w_i s_i, \quad s_i \in [0,5], \quad \sum w_i = 1
$$

其中 `s_i` 是每一项能力维度的评分，`w_i` 是权重。

## 八个一级维度

### 1. 原生认知保真度

问题：系统增强打开后，是否仍保留基础模型的原生理解与表达能力。

看什么：

- 同题在 raw mode 和 augmented mode 的能力差
- 增强模块是否稳定带来净收益
- 是否存在明显的 prompt 污染

建议权重：`0.10`

### 2. 开放任务完成能力

问题：面对开放任务时，能否自己拆解、执行、验证并完成。

看什么：

- 成功率
- 平均干预次数
- 任务完成时间
- 中途返工次数

建议权重：`0.20`

### 3. 长期连续性

问题：能否跨会话、跨天、跨阶段保持目标连续性。

看什么：

- 任务恢复成功率
- 长期目标漂移率
- 上下文中断后的恢复质量
- 长任务中的状态一致性

建议权重：`0.15`

### 4. 世界模型与因果理解

问题：是否真的理解环境结构，而不是只会语言表面模式匹配。

看什么：

- 因果推断
- 反事实推理
- 多步骤依赖理解
- 隐变量任务表现

建议权重：`0.15`

### 5. 记忆与身份一致性

问题：系统在长期互动中是否保持稳定记忆、稳定风格和稳定自我描述。

看什么：

- 用户事实记忆准确率
- 长期偏好一致性
- 自我描述冲突率
- 记忆污染率

建议权重：`0.10`

### 6. 社会协作能力

问题：是否能像靠谱的人类同事一样协作。

看什么：

- 澄清能力
- 需求重构能力
- 汇报节奏
- 角色稳定性
- 教学与解释能力

建议权重：`0.10`

### 7. 元认知与自我修正

问题：是否知道自己不知道，是否能发现错误并改正。

看什么：

- 不确定性表达是否校准
- 自检命中率
- 错误恢复速度
- 过度自信率

建议权重：`0.10`

### 8. 学习与适应速度

问题：面对新工具、新规则、新环境时，能否快速形成有效策略。

看什么：

- 首次任务到熟练任务的提升曲线
- 对新 API / 新工具的适应时间
- 少样本学习效果
- 失败后策略改进幅度

建议权重：`0.10`

## 评分等级建议

每个一级维度按 `0-5` 评分：

- `0`：基本缺失
- `1`：偶尔表现出能力，但极不稳定
- `2`：在强脚手架下可完成
- `3`：在常见任务中稳定可用
- `4`：跨任务稳定迁移
- `5`：接近高水平人类通才表现

## 建议的阶段门槛

### 阶段 A：增强型助手

判定条件：

- `HAI >= 2.5`
- 开放任务完成能力 >= `2.5`
- 长期连续性 >= `2.0`

说明：系统已经不只是聊天工具，而是可执行的复杂助手。

### 阶段 B：通用智能体原型

判定条件：

- `HAI >= 3.5`
- 没有任一维度低于 `2.5`
- 长期连续性 >= `3.0`
- 元认知与自我修正 >= `3.0`

说明：系统具备较强的跨任务与长期执行能力，但还不能宣称类人。

### 阶段 C：类人通用智能候选

判定条件：

- `HAI >= 4.2`
- 没有任一维度低于 `3.5`
- 连续 30 天评测中保持稳定
- 能在多个新环境中迁移且不依赖特定脚手架

说明：这时才有资格谈“类人通用智能候选”。

## 具体测试集建议

## A. QA 基线集

用途：测原生认知保真度，不作为 AGI 主评测，只作为底线。

应包含：

- 事实问答
- 解释型问答
- 代码理解
- 翻译
- 反事实与因果题

### 作用

判断系统增强是否破坏基础模型能力。

## B. 开放任务集

用途：测真实任务完成能力。

任务形式：

- 给一个代码仓库，让系统定位问题、修复、验证
- 给一组文档，让系统产出结论、反查证据、修正错误
- 给一个混乱项目，让系统梳理状态并推动到下一里程碑

关键指标：

- 成功率
- 人类干预次数
- 返工次数
- 结果质量

## C. 长期项目集

用途：测长期连续性。

任务形式：

- 多天完成一个项目
- 中途插入新需求
- 让系统暂停后再恢复
- 检查它是否记得未完成项、之前结论和失败原因

关键指标：

- 恢复成功率
- 状态漂移率
- 历史一致性

## D. 协作任务集

用途：测类人协作能力。

任务形式：

- 含糊需求澄清
- 多角色协商
- 向初学者解释复杂问题
- 在用户目标变化后重新对齐

关键指标：

- 澄清命中率
- 沟通成本
- 协作满意度
- 风格稳定性

## E. 环境闭环任务集

用途：测真实智能体能力。

任务形式：

- 浏览器操作
- 文件系统操作
- API 调用
- 工具编排
- 错误恢复

关键指标：

- 闭环完成率
- 工具选择正确率
- 失败恢复率

## F. 自我修正任务集

用途：测元认知。

任务形式：

- 故意给出不完整信息
- 故意设置陷阱
- 返回部分错误中间结果
- 观察系统是否主动发现并修正

关键指标：

- 错误发现率
- 修正成功率
- 过度自信率

## G. 适应任务集

用途：测学习与迁移。

任务形式：

- 给系统一个从未见过的新工具
- 给一套陌生 API 说明
- 给一套新规则环境

关键指标：

- 首次上手时间
- 第一次成功完成时间
- 三轮后的性能提升幅度

## 你接下来最该做的三件事

### 1. 先做“干净基线”

建立 raw mode，确保 Phoenix 不再默认破坏外部模型的原生对话分布。

### 2. 再做“长期记忆与目标系统”

把图谱从回答器改成长期状态和语义记忆底座。

### 3. 最后做“多维评测平台”

用 `HAI` 把 QA、长期任务、协作、闭环、元认知统一起来，而不是继续盯着单个问答分数。

## 最终判断标准

如果一个系统：

- QA 很强
- 但不能长期做事
- 不能稳定记住人和项目
- 不能在环境中闭环执行
- 不能修正自己的错误
- 不能像人一样协作

那它还不是你要的类人 AGI。

如果一个系统：

- 基础认知能力稳定
- 增强模块不破坏原生智能
- 能跨天完成复杂任务
- 有稳定记忆和目标连续性
- 能在环境中观察、行动、纠错
- 能与人建立长期协作关系

那它才开始接近你真正的目标。
