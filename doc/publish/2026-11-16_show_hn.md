## 3. 正文（英文，可直接粘）

```
Phoenix is a self-hosted agent runtime I've been building for a while. It is not
another wrapper around an API: it runs llama.cpp in-process-adjacent (CUDA,
8B Q4 on a 6 GB GTX 1660 SUPER) and around it implements the parts an agent
actually needs to run unattended for days:

- a mission lifecycle (deadline pressure, self-verdict, helper "boxes" that
  work sub-tasks in parallel, completion judged by the system not by the user)
- a memetic knowledge graph used as the outline/RAG layer, plus a small
  semantic matcher that decides which plugin gets to contribute
- an EFE/MPC planner (optional) that can pick tools and replicate itself
- safety: a latching E-stop, a phrase barrier, per-mission sandboxes
- operations: detached supervisor with health loops, sidecar builds (rebuild
  without stopping the long run), hot config reload, WER minidump + linker map
  crash forensics

Two results from the last week of debugging, both reproducible:

1) GPU utilization was 1-8% and I thought it was a driver problem. It was a
   recursion: the "text-only" backend branch called back into the caller that
   had just reserved a llama slot, so every level took another slot; after
   maxSlots the call returned "slot busy" and no request ever reached the
   server (llama-server log said "all slots are idle"). Fixing that took GPU
   utilization to 85-100% during generation on 3 parallel slots.

2) A heap-corruption crash (0xC0000374) every 10-40 minutes once missions ran
   in parallel. Six concurrency bugs, all in code that a coarse mutex had been
   hiding: a lazily-initialised vector being reallocated while another thread
   iterated it, a process-global std::string written from two missions, an
   unlocked std::map, an unlocked fromJson, a map written outside its lock in
   the tool executor, and finally the one the minidump actually pointed at:
   the search cache erased entries with no mutex while other threads read it.
   The last one was found by rebuilding with -Wl,-Map and resolving the
   faulting thread's return addresses to symbols.

Current state: 8 parallel missions, ~2.4-3.9 h zero-crash windows, 63 targeted
+ 268 wide regression tests green, config hot reload verified live (changed a
population mutation scale from 0.12 to 0.30 in the running process).

Honest limitations: Windows/MinGW only right now, docs are mostly Chinese, the
memetics layer is empirical (no paper for *this* architecture), and the
symbolic-reasoning module is gated off because a demand probe found only 10.8%
of tasks need proofs (below the 20% threshold I set for enabling it).

Repo: <link>
```

## 4. 作者首条评论（HN 惯例：自己补技术细节）

```
Some details people usually ask about:

- Why C++? The runtime owns the GPU process, the scheduler and the memory
  scopes. Allocating a token budget, a mission's KV prefix and a plugin offer
  in one address space is what makes "8 missions on 6 GB" possible; a Python
  layer in the middle would triple the latency of the CPU-side stages.
- The "meme graph": n-gram/phrase nodes with co-occurrence edges, built from
  ingested documents and mission deliverables. It is used for the outline
  (BFS over the strongest nodes), for recall, and for plugin intent: a plugin's
  profile is matched to the situation through meme-cluster overlap, not keyword
  hits.
- Mission model: pressure grows monotonically until the system (or a human)
  reports completion; helper boxes are bounded sub-tasks, and the parent stays
  responsible for the judged artifact.
- On exploration width: the greedy selectors (which expert to summon, which
  file to explore, which memories to recall) all got a temperature + annealing
  or MMR rerank, because argmax locked onto one choice forever.
- Tests: gtest suites for logic engine, plugin semantics, summon ranking,
  explore width, population features, retrieval diversity, mission lifecycle.
```
